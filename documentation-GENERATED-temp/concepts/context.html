Runtime Context

Madj2k\AiCore\Assistant\Context\Context is the central state object for one pipeline execution.

It is intentionally mutable: processors do not return values to the next processor. Instead they read from and write to the context.

Context slots

Slot Type Purpose
Assistant AssistantContext Runtime copy of assistant prompts and connections
Request Request Original query, chat identifier, runtime settings and chat options
History History Conversation history loaded before pipeline execution
Retrieval RetrievalResult Retrieval groups, documents and optimized answer context
Answer AnswerState Candidate and final answer
Current query string Working query that may differ from the original query
Processing trace ProcessingTrace Structured processor-level trace information

Original query vs. current query

The request query remains available through:

$context->getRequest()->getQuery();

The mutable working query is available through:

$context->getCurrentQuery();

Context initializes currentQuery from the request query. QueryOptimizerProcessor can replace it. Passing an empty value to setCurrentQuery() resets the working query to the original request query.

This distinction matters because retrieval uses the current query, while prompt builders can deliberately include both the original and optimized query.

Answer state

AnswerState contains two values:

  • candidate - normally written by AnswerGeneratorProcessor;
  • final - normally written by QualityGateProcessor.

When the pipeline constructs AssistantResponse, it prefers final. If no final answer exists, it falls back to candidate.

Retrieval state

RetrievalResult stores one or more RetrievalGroup instances. This is important when a pipeline performs multiple retrievals: results remain attributable to the processor/query/collection that produced them.

The retrieval state also contains answerContext, which can hold a condensed context generated by ContextOptimizerProcessor.

Processing trace

Processors add trace entries with:

$context->getProcessingTrace()->add(
    event: '...',
    stepId: $step->getUid(),
    input: $input,
    output: $output,
    payload: [],
);

This trace is runtime state and is separate from PipelineLoggerInterface, which provides external logging/observability hooks.

Processor contract

A processor should be understood as a state transition:

Context before step
      ↓
canProcess()
      ↓
process()
      ↓
Context after step

When adding custom processors, document explicitly which context slots they require and which slots they mutate.
